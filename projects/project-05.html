사용자가 문서를 작성하는 동안 입력 맥락을 감지하고, 로컬 문서 검색과 카드 생성을 거쳐 원문 근거가 확인된 추천을 제시하는 전체 사용자 흐름입니다.

01 · Problem Definition

지식 노동자는 스치듯 본 자료를 다시 찾기 위해 주 5.3시간을 검색·전환에 소비하고, 그 결과 재생산에 소요되는 시간의 50% 이상이 "이미 본 것을 다시 찾는" 과정에 낭비된다 (McKinsey · IDC).

기존 검색·챗 기반 도구는 능동적으로 다시 꺼내주지 못하고, 개인 문서를 클라우드로 올려야 해 프라이버시·규제 리스크가 크다. 필요한 것은 작성 중인 맥락을 감지해서 원문 근거가 붙은 카드를 온디바이스에서 스스로 꺼내주는 에이전트다.

02 · Scope & Design Goals

  • 사용자의 작성 맥락 변화를 감지해 관련 개인 문서를 제안하는 Ambient Recall 파이프라인을 설계했습니다.
  • Sparse와 Dense 검색을 융합하고, 재랭킹·구조 신호를 반영하는 Hybrid Retrieval을 구현했습니다.
  • 생성된 카드가 원문에 근거하는지 검증하고, 근거가 부족할 때 질의를 수정하거나 카드를 재생성하는 이중 루프를 구성했습니다.
  • Ollama와 LanceDB가 없는 환경에서도 리팩터링과 회귀 테스트를 수행할 수 있도록 모델-프리 pytest 인프라를 마련했습니다.

* 팀 내에서 제가 담당한 영역은 Retrieval 파이프라인(Hybrid + Rerank + 구조 신호)과 Agent 자기 교정 루프(Corrective / Reflection / Grounding Validator)입니다. Electron UI·디자인·비즈니스 파트는 다른 팀원이 담당했습니다.

03 · System Design & Implementation

담당 영역과 설계 방향

팀 내에서 Retrieval과 추천 Agent 동작을 맡았습니다. 목표는 현재 작성 중인 문장과 비슷한 문서를 찾는 데 그치지 않고, 지금의 상황에서 다음 판단이나 행동에 도움이 될 개인 문서를 능동적으로 제안하는 것이었습니다.

  • Recommendation problem: 문장 유사도와 맥락적 유용성의 차이를 문제로 정의
  • Candidate retrieval: BM25와 GRANITE Vector Search로 로컬 문서 후보를 탐색하고 RRF·reranking으로 정렬
  • LLM relevance judgment: 작성 맥락과 문서 내용을 함께 읽고 현재 상황에 도움이 되는지 판단하는 추천 접근을 비교
  • On-device constraint: 네트워크·외부 API에 의존하지 않는 로컬 환경에서 검색과 추론 비용을 함께 고려

전체 시스템은 Electron Application + Native AI Runtime 2-계층으로 나누어 UI 반응성과 AI 성능(CPU · GPU · Neural Engine)을 분리하고, 100% 온디바이스로 개인 문서가 기기 밖으로 나가지 않도록 설계했습니다. 외부 네트워크와 API를 사용하지 않는 조건은 프라이버시를 높이는 대신 외부 검색·클라우드 모델·도구 연동을 제한했습니다. 이 환경에서 후보 검색과 추천 Agent의 판단 흐름을 담당했습니다.

애플리케이션 UI와 로컬 AI 실행 계층을 분리한 구조입니다. 본인은 로컬 문서 후보 검색, 재랭킹, 추천 Agent의 자기 교정 및 근거 검증 흐름을 담당했습니다.

검색·에이전트 아키텍처와 구현 상세 보기
  • Hybrid candidate retrieval (담당) — BM25 (키워드·수치·전문 용어)와 Vector search (granite-embedding-311m · 768d) 결과를 RRF (Cormack et al., 2009)로 결합했습니다. 이후 Cross-encoder re-ranker와 tier·recency·view 구조 신호를 이용해 후보 순위를 보정했습니다. LLM이 모든 개인 문서를 매번 읽는 대신 검색으로 판단 대상을 좁혀 로컬 추론 비용을 통제하도록 설계했습니다.
  • LLM-based contextual recommendation (비교 실험) — 작성 중인 맥락과 문서 내용을 LLM이 함께 읽고, 주제 일치 여부를 넘어 현재 상황에 참고가 될 문서인지 판단하도록 구성한 접근을 BM25·Vector 유사도 검색과 비교했습니다. 제한된 실제 문서·맥락 비교에서는 BM25·Vector 유사도 검색으로 찾은 후보가 LLM의 단독 맥락 판단으로 선택한 문서보다 더 적합했던 사례가 있었습니다. 다만 평가 표본이 적어 이를 일반적인 우열로 확정할 수는 없었습니다. 이 결과는 문장·주제 유사도와 현재 상황에서의 실질적 유용성이 항상 일치하지 않으며, LLM의 판단만으로 검색 후보를 대체하기보다 검색 결과와 맥락 판단을 별도로 평가해야 한다는 점을 보여주었습니다.
  • On-device trade-off — 외부 API와 검색 도구를 사용하지 않는 로컬 실행 환경에서는 모델 호출 횟수, 입력 문맥 길이, 후보 문서 수가 추론 비용에 직접 영향을 줍니다. 이에 로컬 검색으로 후보를 먼저 압축하고, LLM의 맥락 판단은 제한된 후보에 적용하는 구조를 설계했습니다.
  • Corrective-RAG 외부 루프 (담당) — Query Planning 단계에서 사용자 입력의 의도를 분해하고, Grounding 근거가 부족하면 low_confidence로 판정해 검색 질의를 수정한 뒤 후보 검색을 다시 실행하도록 구현했습니다.
  • Reflection 내부 루프 (담당) — 소형 언어 모델(sLLM)이 생성 카드마다 self-critique를 수행하도록 구성했습니다. 평가 점수가 낮은 카드는 critique-guided regeneration으로 다시 생성하고, 두 차례 재시도 후에도 기준을 충족하지 못하면 keyword 기반 카드로 전환했습니다.
  • Grounding Validator (담당) — 생성된 카드의 각 주장을 원문 청크와 대조해 근거가 부족한 문장을 걸러내고, 검증 기준을 충족하지 못한 카드는 보류 상태로 유지했습니다. 또한 Structured Output으로 카드 스키마를 제한해 출력 형식의 일관성을 높이고 파싱 오류를 줄였습니다.
  • Ingest Pipeline — 개인 문서 → 파싱 → Semantic Chunking → granite-embedding-311m (768d) → LanceDB. 인덱싱은 사용자 노트 폴더 선택 → 권한 설정 → 로컬 sLLM 설치 순서로 온보딩이 진행됩니다.

카드 생성 과정입니다. 검색 후보를 재정렬한 뒤 소형 언어 모델이 카드를 작성하고, 근거가 부족하면 검색 질의를 수정하거나 카드를 다시 생성합니다. 검증을 통과하지 못한 카드는 사용자에게 확정된 정보처럼 노출하지 않도록 설계했습니다.

SMIM 데모 영상입니다. 사용자가 문서를 작성하는 동안 현재 문맥을 바탕으로 개인 문서를 검색하고, 원문 근거를 검증한 추천 카드를 생성해 제시하는 과정을 보여줍니다.

04 · Evaluation & Results

검색 후보 순위 평가: 19개 문서에서 구성한 40개 청크와 10개 질의를 사용한 자체 벤치에서 Vector-only는 MRR@3 0.70, BM25+Vector를 RRF로 결합한 구성은 1.00, 재랭킹과 구조 신호까지 추가한 전체 구성은 0.95를 기록했습니다. BM25를 결합한 단계에서 순위 지표가 가장 높았고, 재랭킹을 추가한 최종 구성에서는 1.00을 넘지 못했습니다. 따라서 재랭킹이 이 벤치의 MRR@3를 추가로 개선했다고 주장하지 않습니다. MRR@3와 Hit@1은 사전에 정한 관련 문서의 검색 순위를 평가한 값이며, 현재 맥락에서의 실질적 유용성을 직접 측정한 지표는 아닙니다.

생성 파이프라인 평가: 26개 카드 생성 E2E에서 21개(81%)는 sLLM 카드로 생성되었고, 5개(19%)는 keyword 기반 폴백으로 처리했습니다. 평균 지연은 17.3초, p95 30.5초였다. 이는 생성 실패를 무조건 오류로 끝내지 않고 대체 경로로 처리하는 동작을 확인한 결과다.

10개 질의로 수행한 자체 검색 실험 결과입니다. 벡터 검색 단독, BM25와 벡터 검색의 결합, 재랭킹과 구조 신호를 추가한 전체 구성을 비교했습니다. 이 결과에서는 BM25를 추가한 구성이 가장 높은 MRR@3를 기록했으며, 재랭킹을 포함한 최종 구성은 별도의 trade-off가 있음을 보여줍니다.
